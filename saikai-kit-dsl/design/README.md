# キットDSLの範囲と責務 — 統合設計案

**状態：提案・未実装。2026-09-28整理。** 仕様例は現行 `kitc.py` では動かない。性能値、キャラクター構成、原作への介入方法の採用決定ではない。

[プロジェクト入口](../README.md) / [記法](language.md) / [時間](timing.md) / [イベント](events.md) / [実装計画](implementation.md)

## 1. 責務の一文

**公開された戦闘機構を使って、技の構成・性能・時間・条件・資源・局所状態・遷移を宣言する。原作への介入、観測、処理順、状態の寿命・復元は実行側が保証する。対応していない要求を別の挙動に黙って置き換えない。**

これは数値設定だけの形式でも、任意のイベントハンドラを書くプログラム言語でもない。既存の素材と実装済みの動作原理から別の技を構成するところまでを対象にする。

## 2. 表現できるべき範囲

| 領域 | DSLで決めるもの | DSLに書かせないもの |
|---|---|---|
| 技構成 | 入力割当、演目、地上空中・方向・形態の選択 | 入力の読み取り、原作actionの呼出し |
| 攻撃 | ダメージ、補正、ダウン、反応、弾・判定の係数 | 衝突検出、原作データの書換え手順 |
| 時間 | 発生・持続・硬直、区間伸縮、再生速度、受付窓 | 元時計と副作用を整合させる実行手順 |
| 移動・防御 | 慣性、突進・後退・落下、効果の区間と係数 | 接地処理、物理・追尾のアルゴリズム |
| 資源・状態 | 弾倉、共有資源、チャージ、段数、時限強化、換装 | 状態保存、予約の整合性、中断時の後片付け |
| 行動連携 | キャンセル、追加入力派生、自動遷移、有限の発射計画 | 再入可能なコールバック、任意の生成関数呼出し |

弾の個数・散布・発射時刻や判定形状も、意味のある調整項目である。現在の原作接続では難しいことを理由に、言語の対象から永久に外さない。対応する生成・判定制御の能力を実装した対象でのみ公開する。

## 3. 状態と繰り返しを許す境界

三段派生、チャージ、時限強化をすべて専用Rust定数へ追い出さない。次を許す。

- スコープと初期値が決まったenum・上限付きカウンター・タイマー・資源・成立履歴。
- 登録済み条件の `all` / `any` / `not` と、型の合う比較。ユーザー定義関数や副作用のある式はない。
- 有限の段、上限付き発射計画、ゲーム時間をまたぐ状態の循環。
- 実装された移動・生成・効果の選択と係数。固有技一つだけが使う部品も認める。

一更新中の無限遷移、無制限の実体生成、任意I/O、メモリアドレス操作は許さない。静的な上限と実行時監視を持ち、超過したら明示的な失敗にする。黙って最後の段やイベントを捨てない。

原則は **値・構成・時刻・条件の変更ならDSL、新しい動作原理・観測方法・介入方法なら実装の追加**。壁反射の原理がなければ実装し、反射回数・減速・寿命を公開する。万能部品を先に作ることも、全固有技をブラックボックスにすることも求めない。

## 4. 記述層と実行層

| 担当 | 責務 |
|---|---|
| `.kit` | 戦闘仕様の宣言。通常は武装表、必要なときだけ詳細を記述 |
| `kitc` | 名前・単位・継承・短縮形を解決し、矛盾・対応能力を検査 |
| 共通rules | 時計、資源、遷移、効果の合成順、入力競合の意味を固定 |
| runtime / adapter | 原作の実行と観測、由来の追跡、適用・復旧・保存・復元 |
| ツール | explain、意味差分、実行trace、設置・実動作との照合 |

共通ルールはキットが利用する契約。キットごとに補正の丸め順や `f` の意味を再定義しない。勝敗・風船・共通覚醒制度などは別のrulesetの責務。キャラクターごとの倍率等は名前付きの拡張点から指定する。

## 5. イベントは事実、キャンセルは入力許可

`fire:first` は実際に発射が成立した履歴。フック位置や履歴用変数の後片付けは作者に見せない。予定発射位置、現在の接地状態、結果確定前のダメージ問い合わせとも区別する。

`cancel` は入力を許す。`followup` は追加入力で同一技の段を進める。`transition` は自動遷移。目的が違うので同じ命令にしない。公開する正確な構文は [language.md](language.md) の提案を基準とする。

一時的な効果は「この段の間だけ」と宣言する。開始で重力を消し、終了で戻す手続きをキットに書かせない。被弾・死亡・復元でスコープが消えた場合も、実行側が効果を残さない。

## 6. 人間に見せる複雑さ

文法は英語の正規名で統一し、日本語は説明・コメント・表示ラベルに使う。構文の日本語別名は持たせない。

単純な調整は次の程度で済ませる。既定値は固定カタログへ解決するので、意味を推測して省略するわけではない。

```text
sub_shot
  ammo reload=300f ?
  frames recovery=12f ?
  cancel into=rush from=fire:first+2f
```

この断片は、基底で技・ルートの入力・発射バッチが一意に解決する前提。曖昧ならIDや入力を要求する。内部実行ID、フック名、保存コードは通常の記法に出さない。

`explain` は省略を展開し、実際の有効値と根拠を表示する。出どころの印は補助情報であり、性能の意味にはしない。提案値を測るrunも許す。

## 7. 正しさと検証の境界

コンパイル成功は「意味を解決でき、対象が対応を宣言している」こと。設置成功、実機での再現、巻き戻し一致とは別に検証する。

型・参照・矛盾・実現不能はエラー。強すぎる・弱すぎる・永久コンボの疑いなどは原則分析や警告。バランスの好みを不正な仕様と混同しない。

一方、未観測の命中を予測で埋める、発生短縮にアニメ全体倍速を黙って使う、未対応項目を捨てる、といった「それらしい近似」は禁止する。意図的に近似を採る場合は別の名前付き契約にする。

## 8. 過去案からの訂正

| 過去の案 | 統合案 |
|---|---|
| 日本語/英語の構文別名を併用 | 英語ASCIIの構文へ統一。日本語の説明・コメント・表示ラベルは維持 |
| 技を `PerfId` に統一 | `MoveId` と素材の `PerfId`、一回の実行IDを分離 |
| 状態・条件・繰り返しを持たない | 型付き局所状態、閉じた条件式、上限付き計画を認める |
| キャンセルはイベント基準が基本 | 絶対フレーム、実イベント、区間、元演目位置を同格にする |
| 当たりの表引きは追加状態なし | 計算は純粋にできても、発生元・命中取引・履歴は状態 |
| 数値系はすぐホットリロード可能 | 実行中の技・弾の版と共有資源の移行を別途管理 |
| 弾の数・散布・発射時刻は対象外 | 生成能力の実装後に公開できる言語の対象 |
| コンパイラが受理したら使える | 型検査・能力宣言・設置・実機・再実行を別々に確認 |

本案の提案同士に矛盾が出た場合、この責務定義を上位に置き、各専門文書を更新する。初期調査の事実を後の設計判断で書き換えない。
