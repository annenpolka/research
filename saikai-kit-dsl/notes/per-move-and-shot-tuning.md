# 技と弾の個別調整：調査記録と統合案への訂正

初期調査の基準はdaybreak-saikai `abe253c`。以下の事実欄は当時の文書・台帳・コードの調査記録で、現在HEADの保証ではない。実機で新たな確認は行っていない。

**現在の設計提案の入口は [design/README.md](../design/README.md)。** 本メモの後半は、初期提案をそのまま重ねず、後の議論で訂正した方針に差し替えた。言語の表現範囲と、現時点の実装難度を区別する。

## 事実：初期調査

### 原作で技と弾のデータがある場所

- **技の時間**：sequence の番号と整数の時計で決まる。時計は action（仮想 slot 6）の末尾で 1 ずつ進む。判定の keyframe、姿勢、コードの中のフレーム判定も、この時計で決まる（F30）。実機でも、判定は DAT の `key_tick` の時計の値で出た（F31）。
- **当たりの中身**：keyframe ごとの hit words（20 語）にある。基礎ダメージ、よろけ（7）、ダウン値（8、Wiki の値×20）、味方への％（3）、ヒットストップ（攻撃側 9・被弾側 10）、反応の行動 id（13・14）、吹き飛びの速さ（17・18）など（F32、`docs/combo.md`、`docs/react.md`、`docs/friendly.md`）。
- **弾**：弾番号から、manager の 4 つの定義表（`+0x34`・`+0x38`・`+0x3C`・`+0x40`）が引かれる。弾の毎 tick の処理（0x5F7BE0）は、持ち主の manager の種類（46 通り）と弾の種類（`+0x150`）で分かれるコード（`docs/reports/weapon-mixing-static.md` §2、`docs/homing.md`）。鉈の NS の弾は、最初の tick に速さ 37.5。これがデータかコードの即値かは、まだ読まれていない。
- **弾数**：持ち物の弾ごとの 12 バイトの表の `+8` にある（F139）。

### 初期調査時の調整項目

| 層 | 技・弾ごとの鍵 |
|---|---|
| 慣性、ブースト消費 | 演目名、武装名 |
| COMBOの補正率・ダウン値 | 原作行動idと弾種。鉈managerのactorだけ |
| REACTの反応 | 演目名と連鎖の段 |
| 弾倉 | コマンド名 |
| 誘導 | 全体で一つ。鉈の弾種0・10だけ |
| フレーム調整 | 借用技S0のみ。sequence・keyframeの生番号 |

当たりの接点はKakeraの `hit_begin/hit_reaction/hit_damage/hit_team`。技処理はactorのvtable写し、弾処理は借用クラスごとの `ENTITY_VTS` を使える。

keyframe書換えと早送りは借用特格331での実機記録F37がある。基準計測、停止カウンター保持、track差替えにはN7の未確認項目がある。この記録を全演目の任意retimeの実証に拡張しない。

当初の資料は、コード分岐で生成される発射時点はデータ編集だけでは動かないとし、交差判定形状は未確定、新しいアニメの制作は範囲外としていた。行動対応表は16キャラクター・46武器分があり、`tools/moves/build_table.py` が生成する。

初期調査の詳細と旧提案は[本メモの固定版](https://github.com/annenpolka/research/blob/92ad6cadc3a0ebe8d998dd8b05d52e250982cc47/saikai-kit-dsl/notes/per-move-and-shot-tuning.md)を参照。F/N等は当時のsaikai台帳の識別子で、本編集で再測定した結果ではない。

## 推測（示唆）：統合後の方針

### 技と素材の名前は統一しない

MoveId、PerfId、攻撃定義ID、一回の技実行IDを分ける。同じ演目を別技・強化版・別配置で使えても、性能や履歴を混同しない。`hit slash_1` 等の登録名を使い、コメントと衝突する `nata.melee#2` は採らない。[記法](../design/language.md)を参照。

### 表を引く処理と、そのための状態を分ける

ダメージ計算自体は純粋にできるが、その命中がどの技・弾・設定版に由来するかは自動では分からない。由来、命中取引、発射バッチ、成立履歴、保存復元を必要な範囲で実装する。「表引きだから追加状態なし・そのまま巻き戻せる」とは扱わない。[イベント](../design/events.md)を参照。

### 時間は目標だけでなく複数の操作で指定する

絶対フレーム窓、実イベント相対、区間境界、元演目位置を同格にする。`frames`、`retime`、`animation`、移動の保持方針を区別する。source通過の観測と、原作の副作用を保つ時間変形は別能力。[時間](../design/timing.md)を参照。

### 生成・判定の制御は将来の言語対象

弾数・散布・発射時刻は既存の数値表の変更では足りない可能性があるが、対応する生成機構を実装した後はDSLから指定してよい。新しい動作原理はコードで実装し、その構成と係数を公開する。判定形状も同様。アニメ素材の新規制作そのものはDSLの責務ではない。

### 読替えと導入順

数値だから即時読替えしてよいとはしない。最初はリセット境界で全体適用し、技・弾の設定版と共有資源の移行を別に管理する。

「当たり→弾→時間→判定」の単純な難度順から、**入口の信頼性→同定と時計→必要な実イベント→構成可能な行動→実証済みの高度操作**へ整理する。絶対窓は全イベント完成を待たない。現在の詳細は [実装計画](../design/implementation.md)。
