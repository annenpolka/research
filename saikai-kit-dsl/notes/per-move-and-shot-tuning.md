# 技と弾を個別に調整できるようにするには（設計メモ）

キットの紙（`.kit`）で、技や弾ごとに数値を調整できるようにする場合の見通し。saikai 側の改修をしてよい前提で考えた。
読んだのは daybreak-saikai `abe253c` の文書・台帳・コード。実機では何も確かめていない。

## 事実

### 原作で技と弾のデータがある場所

- **技の時間**：sequence の番号と整数の時計で決まる。時計は action（仮想 slot 6）の末尾で 1 ずつ進む。判定の keyframe、姿勢、コードの中のフレーム判定も、この時計で決まる（F30）。実機でも、判定は DAT の `key_tick` の時計の値で出た（F31）。
- **当たりの中身**：keyframe ごとの hit words（20 語）にある。基礎ダメージ、よろけ（7）、ダウン値（8、Wiki の値×20）、味方への％（3）、ヒットストップ（攻撃側 9・被弾側 10）、反応の行動 id（13・14）、吹き飛びの速さ（17・18）など（F32、`docs/combo.md`、`docs/react.md`、`docs/friendly.md`）。
- **弾**：弾番号から、manager の 4 つの定義表（`+0x34`・`+0x38`・`+0x3C`・`+0x40`）が引かれる。弾の毎 tick の処理（0x5F7BE0）は、持ち主の manager の種類（46 通り）と弾の種類（`+0x150`）で分かれるコード（`docs/reports/weapon-mixing-static.md` §2、`docs/homing.md`）。鉈の NS の弾は、最初の tick に速さ 37.5。これがデータかコードの即値かは、まだ読まれていない。
- **弾数**：持ち物の弾ごとの 12 バイトの表の `+8` にある（F139）。

### saikai が今、技や弾ごとに持っている調整（鍵の形がばらばら）

| 層 | 技・弾ごとの鍵 |
|---|---|
| 慣性（`SAIKAI_INERTIA`）、ブースト消費（`SAIKAI_BOOST_COST`） | 演目名、武装の名前 |
| 補正率・ダウン値の上書き（`SAIKAI_COMBO` の `melee301=`・`shot110=`） | 原作の行動 id と弾の種類。鉈の manager の種類の actor だけ |
| 反応の種類（`saikai-rules::react::KIT`） | 演目名とその連鎖の段 |
| 弾倉（`SAIKAI_AMMO`） | コマンド名 |
| 誘導（`SAIKAI_HOMING`） | 鍵なし（全体で 1 つ）。効くのは鉈の弾の種類 0・10 だけ |
| フレームの調整（`SAIKAI_TUNE`） | 借りた技（S0）だけ。書き方は sequence・keyframe の番号の生の値 |

### 当てる継ぎ目はもうある

- **当たりの口**：カケラが貸す `hit_begin`・`hit_reaction`・`hit_damage`・`hit_team`。COMBO・REACT・HP・FRIENDLY が使っている。
- **技の処理と操作の差し替え**：キットの枠の actor の vtable の写し（`s0::ACTOR_VTS`）で、action と controller の trampoline を通せる。
- **弾の処理**：弾の vtable の写し（`ENTITY_VTS`）を、借りる武器のクラスごとに作れる。

### 時間を動かす手段の状態

- 確かめ済み：keyframe の書換え（C）と早送り（A）。借りた特格 331 で実機を回した（F37）。
- 未確認：基準の計測、停止カウンターでの保持（B）、track の差し替え（D）。N7 の 1〜4 が残っている。

### データでは動かせないと書かれているもの

- 射撃の発射の時点：生成がコードの分岐なら、データでは動かない（`docs/kit-model.md`「フレームの調整」）。
- 判定の形：原作の交差判定の形が未確定。
- 新しいアニメ：範囲外。

### 材料

行動対応表（`docs/moves/*.md`）は 16 キャラクター・46 武器ぶんある。発生・持続・全体・硬直・ダメージ・ダウン値・弾が、実測と DAT の照合で載っている。`tools/moves/build_table.py` が作る生成物。

## 推測（示唆）

### 1. 最初に、技と弾の名前をそろえる

- **技は演目名（`PerfId`）に統一する。** 連続技の何段目の当たりかは `nata.melee#2` のように指す。COMBO の `melee301` のような原作の番号はやめる。
- **弾に「弾の名前」（仮に `ShotId`）を足す。** 例は `nata.shot.blade`。演目表と同じく、runtime の表で `(クラス, 弾番号, 弾の種類)` に訳す。

根拠：今の鍵はばらばらで、紙から「サブの弾」を指せない。原作の番号を rules に出さない決め（J11・J15）とも、これで揃う。語彙は行動対応表から生成できるので、`vocab.json` の手写しも要らなくなる。

### 2. 調整は、書き換える場所の違いで 4 段に分かれる

| 段 | 調整するもの | 当て方 | 難しさ |
|---|---|---|---|
| A. 当たりの数字 | ダメージ、ダウン値、補正率、よろけ、反応の種類、味方への％ | 当たりの口で、当たりごとに答える。COMBO・REACT・HP・FRIENDLY を「演目名と段」「弾の名前」の表から引く形にまとめ直す | 低い。継ぎ目も前例もある。当たりごとの純関数で追加状態が無く、巻き戻しにも強い |
| B. 弾の挙動 | 速さ、誘導の強さ、寿命（距離）、誘導を切る条件 | 弾の vtable の写しを、ベースのクラス自身の弾にも付ける。弾の名前ごとに、HOMING の設定一式と速さを持たせる | 中くらい。37.5 がデータかコードかの静的な読みと、水鉄砲の弾の種類の実測が要る |
| C. 時間 | 発生、全体、硬直、キャンセルの受付 | `SAIKAI_TUNE` の早送りと keyframe の書換えを、キットの全演目へ広げる。紙には「発生 18→14」のように目標を書き、runtime が行動対応表の実測から変形を導く | 高め。N7 の残りと、命中したときの振る舞いを実機で確かめる必要がある |
| D. 判定の形・位置、ヒットストップの長さ | keyframe の点 A・B と大きさ、hit words 9・10 | sequence の写しを技の間だけ差し替える。ヒットストップは、当たりの口で停止カウンターを書き直せるかを先に読む | いちばん高い。交差判定の形、DAT の読み直しで写しが解放される問題、共有の穴（U9）がある |

- **弾の数・拡散・発射の時点は、4 段のどれにも入れない。** クラスごとのコードの分岐なので、データの調整では届かない見込み。やるなら生成そのものを saikai が持つことになり、危険が大きい。

### 3. 紙と saikai の間の形

- **紙はこうなる**：

  ```text
  サブ
    perf    nata.backstep_shot
    frames  startup 18→14                  ?U
    hit 1   damage 1200 down 1.5 react stagger
    shot blade  speed 30 homing turn=1.2/0.6 life 60
  ```

- **v0 のままでは書けない。** saikai 側に、調整表を 1 つ読む口が要る。例は `SAIKAI_TUNING=@<ファイル>`。
  - rules に「演目名と弾の名前 → 調整」の型を置く。
  - runtime は、段 A〜D の書き換える場所で、その表を引くだけにする。
- **遊びながら直すときの効き目**：
  - A と B は、読み直した次の当たりや次の弾からすぐ効く。当たりごとに答えるだけで、状態を持たないから。
  - C と D は、次にその技を出したときから効かせる。技の途中で表が替わると、時計と判定がずれるから。
- **数値の尺度は紙で決めておく必要がある。** 例：ダメージを原作の 10000 の尺度で書くのか、耐久値の `unit=` の尺度（J74）で書くのか。U71 の続きで、ユーザーの判断になる。

### 4. 順番

- **A → B → C → D の順を推す。** 根拠：A と B だけで、「この技の火力とダウン値、この弾の速さと誘導」という手触りの調整の大半が手に入る。しかも既存の継ぎ目の延長で、実機の未確認の部分に賭けずに済む。C は N7 の実機の計測と一緒に進める。D は C が安定してからでよい。
- **最初の一手**：COMBO の技ごとの上書き（今は鉈の行動 id が鍵）を、演目名と段の鍵へ移す。段 A の見本になり、1 の名前の統一も同時に試せる。キャラクターの調整の中身にかかわるので、着手はユーザーの判断による。
