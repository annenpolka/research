# いまの接続手順（daybreak-kakera `bf03c1ea`）

daybreak-kakera の main `bf03c1ea`（2026-09-27）の文書から、人が実際に手を動かす手順を抜き出した。数えたのは「人がやること」で、プログラムの内部処理は数えていない。出典はすべて daybreak-kakera 側のファイル。

## 事実

### 版をそろえる（接続の前）

出典：`docs/windows-package.md`

1. 公開済みの 40 桁の commit を、誰かが全員に伝える。
2. 各自が `git fetch origin`、`git checkout --detach <commit>`、`py -3.13 tools/fetch_binaries.py --launch` を実行する。
   - package は HEAD と完全に同じ SHA のものしか取らない。未公開なら 404 で止まり、近い版で代用はしない。
   - 版の違いを拒否する仕組みとして文書にあるのは、どれもコードを交換して接続した後のもの：対戦前通信の版（core lobby 通信版 4。`crates/kakera-launcher/README.md`「固定入力ディレイ」）、GGRS の bootstrap と演算設定の照合（STATUS F201）。古い実行ファイルは新しい v2 コードをそもそも読めない（`crates/kakera-connect/README.md`）。接続の前に相手のビルドを突き合わせる手順は、文書では見つからなかった。

### 2 人接続（GUI）

出典：`crates/kakera-launcher/README.md`「GUI のコード交換」

| # | 招待側 | 参加側 |
|---|---|---|
| 1 | 「2人接続」を選ぶ。入力ディレイ（0〜4）を選ぶ | 「2人接続」を選ぶ |
| 2 | 「招待を作る」→ 招待コードをコピー → チャットに貼る | |
| 3 | | チャットから招待コードをコピー → GUI に貼る → 「参加する」 |
| 4 | | 返信コードをコピー → チャットに貼る |
| 5 | チャットから返信コードをコピー → GUI に貼る → 「返信を受け付ける」 | |
| 6 | 接続後、両側の原作が対戦前画面から起動する | 同左 |

- **人が運ぶもの**：長いコード 2 本（招待と返信）。向きは招待側→参加側、参加側→招待側の 1 往復。
- **期限**：コード交換を含めて約 5 分。やり直すときは新しい招待から始める。コードは使い捨て。
- **コードの中身**：`kakera-connect-v2.` + zlib 圧縮した JSON の base64url。JSON には SDP がまるごと入る（ICE の一時資格情報、候補のアドレス、DTLS の fingerprint）。そのため「信頼できる私的な経路で交換する」と定めている（`crates/kakera-connect/README.md`「Signaling and authentication」）。
- **長さ**：報告は合成 SDP で 1118→568 文字（`docs/reports/internet-connect.md`「コードの短縮」）。この研究で実物を測ると、ループバックで候補行が 2 行だけのときでも、招待は 646〜657 文字、返信は 706〜714 文字あった（`results/measurements.json`）。WAN（host 4・srflx 2 の候補）では、招待は約 810 文字になる見込み（推定。後述）。
- **実際の運び方**：別回線の二端末の検査（GI-host-001／GI-peer-001）では、「招待・返信コードを私的なファイルとチャットで交換」した（`docs/reports/internet-connect.md`「異なる回線の二端末」）。

### 4 人接続（GUI）

出典：`crates/kakera-launcher/README.md`「4人接続」

| # | 招待側 | 参加者 2・3・4 |
|---|---|---|
| 1 | 「4人接続」を選ぶ → 「招待を作る」 | 各自「4人接続」を選ぶ |
| 2 | 「招待側の受付枠」を 2→3→4 と切り替え、そのつど表示される招待コードを各人へ送る（3 回） | |
| 3 | | 自分宛ての招待を読み込み →「参加する」→ 返信コードを招待側へ送る |
| 4 | 参加者を選び、届いた返信を貼って受け付ける（3 回） | |
| 5 | 6 組の直接接続がそろったら原作を起動する | 同左 |

- **人が運ぶもの**：長いコード 6 本。すべて招待側を通る。
- **期限**：2 人と同じ。同じ返信の再受付はできず、やり直すときは接続を終了して新しい招待を作る。

### 方針（ユーザー判断）

- **J36**：初版の接続情報は、サーバー不要の招待コード・返信コードで交換する。TURN と常設のマッチングサービスは初版に含めない。直接接続できない回線の組合せがあることは許容する。
- **`docs/plans/internet-connect.md`**：独自の NAT 越えや暗号は実装しない。自動接続に失敗しても、原作 DirectPlay や手動 UDP へ黙って切り替えない。

## 推測（示唆）

- **手間の中心は「長いコードを人が往復で運ぶこと」にある。**
  - 根拠：上の表で、人の操作の大半はコピー・貼り付け・送信・受付。2 人でも、参加側が返信を作れるのは招待を受け取った後なので、二人とも同時にチャットの前にいる必要がある。
- **4 人では、招待側が直列のボトルネックになる。**
  - 根拠：6 本がすべて招待側を通り、受付枠の切り替えと受付を 3 回ずつ繰り返す。そのあいだも 5 分の期限は一つで、全員の交換がその中に収まらなければならない。
- **5 分の期限が、人の手際の期限にもなっている。**
  - 根拠：connector は「招待を作る」で起動し、`--timeout-secs`（既定 300 秒）は「コード交換と接続試行の全体」を縛る（`crates/kakera-connect/README.md`「Commands」）。一方、招待コードの中身（ICE の資格情報）は、その connector が作るものなので、今の方式では起動を遅らせられない。
- **版の不一致は、分かるのが遅い。**
  - 根拠：上に挙げた拒否は、どれもコードの交換（と多くは接続）の後に起きる。そこまでの交換は無駄になり、原因が「版の違い」だと分かる表示になるかも場合による（コードが読めない、通信版が違う、bootstrap が違う、の三通り）。
